## 3. Kiro 输出演变

### 3.1 Kiro 第一版（初稿）

**产出**：10 个状态、10×10 转换矩阵、retry/timeout 策略、terminal 定义。

**发现 5 个问题**：
1. 引用了不存在的 `message`/`metadata`/`status` 字段
2. `orphaned → deleted` 矩阵矛盾（未标注 manual）
3. `failed_permanent` 无法回到 `pending`（设计选择需确认）
4. `max_retry=3` 表述歧义（含首次执行）
5. `orphaned` 进入条件不可操作（V1 无检测能力）

### 3.2 Kiro 第二版（严重回归，不可用）

**5 个致命问题**：
| # | 问题 |
|---|------|
| 1 | 状态数从 10 降为 8（丢失 `skipped`、`disabled`） |
| 2 | `in_progress` 被改为 `syncing`，与 `config.py` 枚举和 DB CHECK 约束不一致 |
| 3 | 编造了不存在的 `sync_tasks` 表及 `retry_count`、`next_retry_at` 等字段 |
| 4 | 编造了不存在的 `sync_result` 值 `permanent_failure` |
| 5 | 10×10 矩阵退化为列表，无法校验完整性 |

**根因**：Kiro 每次 `chat --no-interactive` 均无会话记忆。修订 prompt 未重新列出完整上下文（10 状态、现有 schema 等），导致模型从零重写。

**系统性缺陷确认（第 3 次）**：Kiro 收到修改/修订请求时倾向从零重新生成而非增量修补。适合首版输出，不适合增量修订。

## 6. 最终状态机设计基线（v4）核心规则

### 6.1 10 状态确认

**terminal=true（引擎绝不自动推进）**：
`synced`、`failed_permanent`、`skipped`、`disabled`、`deleted`

**非 terminal（引擎可自动推进）**：
`pending`、`in_progress`、`failed`、`stale`、`orphaned`

### 6.2 关键过渡规则

| 规则 | 内容 |
|------|------|
| `synced → stale` | 仅由 `payload_hash` 不匹配触发，对应 `sync_result=drift_detected`。TTL 自动过期不作为 Phase 5 结论（→ C1） |
| `orphaned` 进入 | Phase 5 仅支持 manual 标记（除 `deleted` 外的任何状态）。`pending → orphaned` 需 `external_id` 已存在 |
| `orphaned → deleted` | Phase 5 标注为 manual（API 手动清理），auto 为 future |
| `failed_permanent → pending` | 明确允许 manual 管理员强制重置，引擎绝不自动推进 |
| `timeout` 后目标状态 | 取决于当前 `sync_attempt`（≤3 → `failed`，≥4 → `failed_permanent`），确保不绕过 max_retry 上限 |

### 6.3 sync_attempt 编号规则

- `sync_attempt=1`：首次尝试
- `sync_attempt=4`：第 4 次尝试（第 3 次重试），若仍失败则进入 `failed_permanent`
- 不可重试错误直接进入 `failed_permanent`，不计入 attempt 计数
- 计数基于 `sync_logs.sync_attempt` 字段计算

### 6.4 deleted 语义

- 状态机角度：`status=deleted` 是软删除终态，记录保留
- 物理清理：`DELETE FROM sync_state` 是独立的数据库维护动作，不属于状态机范围
- 二者严格分离，不得混淆

### 6.5 in_progress 超时检测

- Phase 5 使用 `sync_state.updated_at` 作为近似起点（`pending → in_progress` 时自动更新）
- **已知风险 R1（中）**：`updated_at` 可能被其他字段更新覆盖。若编码阶段发现此路径，必须改用 `sync_logs.created_at`（现有字段）或新增 `started_at`/`locked_at`，否则不得上线
